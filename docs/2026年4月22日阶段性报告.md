**报告人**：袁康睿

## 一、已完成工作总览

### 1.1 数据工程（已闭环）
- **原始数据**：10.5GB工业线扫长图（分辨率1326×5006），LabelMe JSON标注。
- **预处理流水线**：编写`prepare_dataset.py`，实现：
  - 滑窗切割（窗口640×640，步长500），将长图切分为标准训练子图。
  - LabelMe JSON → YOLO TXT格式转换，通过IoU阈值判定保留有效标注。
  - **负样本保留机制**：随机保留约10%无瑕疵子图，仅生成图片不生成标注，防止模型过拟合木纹背景。
- **最终数据集**：训练集3287张，验证集822张，类别数3（defect_2点状瑕疵、defect_3中型瑕疵、defect_6大型/边缘瑕疵）。

### 1.2 模型训练与实验（已完成三轮完整训练）
| 实验编号 | 模型配置 | 训练轮次 | 最终mAP50 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| **Exp-01** | YOLOv8n（Baseline） | 50 | **0.5855** | 基线模型，所有后续对比基准 |
| **Exp-02** | YOLOv8n + CBAM + WIoU | 100 | 0.5711 | 魔改实验，精度未超越基线 |
| **Exp-03** | YOLOv8n + 数据增强调整 | 50 | 0.4466 | 调整mosaic/copy_paste等参数，精度大幅倒退 |

- **Exp-02关键发现**：CBAM插入在Head的P3层，其全局池化机制导致小目标（defect_2）特征被淹没，AP从0.417进一步下降至0.362；WIoU默认超参数（γ=1.9）在小规模数据集上引发收敛困难。
- **Exp-03关键发现**：降低mosaic至0.3后，训练样本多样性骤减，在未同步调整学习率的情况下，模型收敛受阻，验证了数据增强参数与优化器协同调整的必要性。

### 1.3 部署验证（已闭环）
- **推理加速**：成功将Baseline模型导出为OpenVINO格式，在Intel Core Ultra 7 155H（纯CPU）上实现：
  - 纯推理FPS：**107.32**
  - 平均单张推理耗时：**9.32 ms**
- **结论**：模型轻量化与推理速度已完全满足DK2500实时检测需求（目标FPS≥50）。

### 1.4 工具链与工程化
- 建立完整的命令行训练/验证/推理脚本集（`prepare_dataset.py`、`start_training.py`、`val_baseline.py`、`infer_openvino.py`、`full_compare_openvino.py`）。
- 完成项目Git版本控制与GitHub推送。

## 二、当前核心瓶颈定位

### 2.1 精度瓶颈
- **整体mAP50**：0.5855（Baseline Exp-01）
- **各类别AP50**：
  - defect_2（点状小瑕疵）：**0.417** ← **核心短板**
  - defect_3（中型瑕疵）：0.689
  - defect_6（大型/边缘瑕疵）：0.653

**根本矛盾**：小目标（defect_2，面积通常<10×10像素）在复杂木纹背景下特征微弱，现有YOLOv8n的P3/8特征图空间分辨率不足，且CBAM等通用注意力机制因全局池化会进一步淹没小目标特征。

### 2.2 算力与时间约束
- **当前训练环境**：本地笔记本CPU（Intel Core Ultra 7 155H），单轮训练约8分钟。
- **完整训练耗时**：100轮约13-14小时，300轮需近一周。
- **实验迭代效率**：每轮完整实验时间成本高，限制了多方案并行探索。

## 三、当前形势评估

### 3.1 已有成果的价值
1. **工程链路全通**：从数据预处理、模型训练、精度验证到OpenVINO部署，形成可复现、可交付的完整流水线。
2. **Baseline模型可用但不足**：mAP50 0.586在初版工业质检中属于合格起点，但距离高端产线要求的≥0.85仍有显著差距。
3. **失败实验的高价值归因**：Exp-02和Exp-03的失败并非无用功，它们精准排除了两条看似可行实则不适配的技术路线（CBAM+WIoU、孤立调整数据增强），为后续优化提供了明确的反向约束。

### 3.2 面临的核心抉择
- **选项A：交付现状**。将Baseline模型交付队友进行DK2500部署验证，项目进入集成测试阶段。优点是无额外时间成本，缺点是模型精度未达团队预期。
- **选项B：继续攻坚精度**。在现有基础上投入更多算力与时间，通过已被工业界验证的技术组合（见第四章）将mAP50推至0.75以上甚至0.85。优点是对项目质量有更高追求，缺点是需要额外4-7天时间及可能的云端算力开支。

## 四、可能的下一步行动（技术路线详述）

若选择继续攻坚精度，以下三条路线按**投入产出比与成功率**排序。

### 4.1 路线一：保守优化——在YOLOv8n框架内极致挖掘（推荐优先执行）
**目标**：在不改动模型结构的前提下，通过训练策略优化将mAP50提升至0.65左右。

| 优化项 | 具体措施 | 理论依据 | 预期收益 |
| :--- | :--- | :--- | :--- |
| **延长训练轮次** | 将Baseline从50轮继续训练至150轮 | 小目标收敛慢，50轮远未到饱和点 | +3~5点 |
| **学习率调度优化** | 启用余弦退火（`cos_lr=True`），增加预热轮次 | 平滑后期收敛，避免震荡 | +1~2点 |
| **定制锚框** | 使用K-means++对训练集标注框聚类，生成定制锚框 | 更匹配瑕疵长宽比分布 | +2~3点 |
| **关闭Mosaic后期** | 最后20轮关闭Mosaic，让模型适应原图分布 | 减少训练-推理分布差异 | +1~2点 |

**总预期收益**：mAP50从0.586提升至**0.63-0.67**。  
**时间成本**：基于现有`last.pt`继续训练100轮，约14小时。  
**风险**：极低，无需修改代码。

### 4.2 路线二：结构微调——引入P2检测头与CA注意力
**目标**：针对性解决小目标漏检，将defect_2的AP提升至0.55以上，整体mAP50冲击0.72-0.78。

| 组件 | 具体实施 | 理论依据 | 预期收益 |
| :--- | :--- | :--- | :--- |
| **P2检测头** | 修改YOLOv8n.yaml，增加160×160高分辨率检测层 | 为微小目标保留空间细节，防止下采样丢失 | defect_2 AP +15~20点 |
| **CA注意力** | 替换CBAM，将CA模块插入Backbone的C2f层后 | 保留精确位置信息，对小目标友好 | mAP50 +3~5点 |
| **冻结训练** | 前30轮冻结Backbone，仅训练新增模块；后70轮全局微调 | 规避随机初始化模块对预训练权重的破坏 | 保障收敛稳定性 |

**总预期收益**：mAP50提升至**0.72-0.78**。  
**时间成本**：全新训练150轮，纯CPU约25小时；建议租用云端GPU（如AutoDL RTX 4090）压缩至2-3小时。  
**风险**：中等，需正确修改配置文件并注册CA模块。

### 4.3 路线三：规模升级——切换至YOLOv8s + 路线二的完整组合
**目标**：以更大的模型容量承载P2检测头和CA注意力，追求mAP50≥0.85。

| 组件 | 具体实施 | 预期收益 |
| :--- | :--- | :--- |
| **YOLOv8s** | 参数量从3M升级至11M，仍在DK2500 NPU可承受范围 | mAP50基础提升5~8点 |
| **P2检测头 + CA注意力** | 同路线二 | 同路线二 |
| **300轮充分训练** | 配合云端GPU | 充分收敛，挖掘全部潜力 |

**总预期收益**：mAP50达到**0.82-0.88**。  
**时间成本**：云端GPU约6-8小时；本地CPU约4-5天。  
**风险**：模型规模增大可能略微影响推理速度（预计FPS从107降至70-80，仍远超50目标）。
